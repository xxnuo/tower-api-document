# Tower MCP 反馈复验

2026-11-19 使用反馈中的同一授权账号、团队、成员、项目、任务清单和活动游标，在本地网关连接真实 Tower 做只读复验。旧版为 `c94e7f5`，新版为 `e874092`。原会话的调用明细无法核实，下表为复跑结果。Tower 内容和权限在复跑期间可变。

每格调用数为 **MCP 工具调用 / Tower 上游 HTTP 请求**。按用例独立调用，包含表中列明的探针和解决问题所需的补查。一次 `tools/call` 算一次 MCP 调用。网关出站 RoundTripper 每发出一次到 Tower 的请求记一次，含重定向、刷新、补页和内部并发请求。合计取每项的有效对照运行，排除环境准备、本地健康检查和为核对结果另行发起的补测。原反馈里的资源标识、任务内容、签名链接和账号凭据不进入本报告。

## 缺陷造成的额外调用

有直接实测对照的旧版额外调用共 **19 次 MCP / 19 次 Tower HTTP**。其中第 1 项 4 次用于补查成员分页，第 4 项 12 次用于逐条补齐列表遗漏的时间字段，第 5 项 3 次用于拉完待办后筛选。第 4、7 项原提示已要求的详情对照、各场景的诊断探针、真实数据分页均未计为缺陷成本。在新版中，改用表内的修复路径后，上述 19 次补查均可省略。第 8 项将客户端按清单翻页换成项目游标，另少 13 次 MCP 调用。这个差值单列，因为两种流程都要向 Tower 读取项目数据。原始 14 项历史调用的缺陷成本未知。

## 如何重跑

1. 使用反馈中的同一组资源、关键词「用户反馈」和 2026-11-19 截止日期。从相同授权状态建立两个本地网关进程，各用独立的 SQLite 副本。所有工具只使用查询操作，`raw_request` 一律为 GET。
2. 在两个进程的 HTTP Transport 中只对 Tower 主机记录每次出站事件，由测试客户端在每个独立场景前后计数。每个事件只需一个固定标记。测试客户端只保留计数、字段存在性、分页标志及数据比较结果。
3. 第 8 项统一传 `completed_todo=true`；旧版先列清单，再逐一用 `list_todos(page_size=50)` 翻页；新版用 `list_project_todos(page_size=50)` 跟随 `next_cursor`。两侧都按任务 ID 去重。第 2 项同时保留反馈的历史游标和现场新游标，以便区分对应数据随时间变化的情况。
